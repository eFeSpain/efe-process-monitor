# Run at boot on Linux: `--install-service` — design

Date: 2026-11-08 · Status: approved in conversation, pending written review · Target: 0.5.0

## Goal

The persistence the audit looks for runs at boot; a monitor that only runs when
someone launches it misses exactly that moment, and everything that happens
while nobody has started it. After this change the monitor can be installed as
a systemd system service: it is watching before anyone logs in, and when a user
logs in the tray icon, the desktop notifications and "open panel" attach to that
session. Installing and removing it needs no hand-edited files.

Scope of this delivery: **Linux with systemd**. Windows (a service in session 0
plus a helper in the user session) is a second delivery with its own design.

## What exists and is reused

- `desktop_linux.go`: as root, desktop work runs *as the logged-in user* —
  `desktopUser()` (resolved once, from `SUDO_UID`/`PKEXEC_UID` or the single
  `/run/user/<uid>/bus`), `sessionFor` (credentials + session env from a process
  of theirs with `WAYLAND_DISPLAY`/`DISPLAY`), `runAsDesktopUser`, and the tray
  helper: a copy of the binary run as the user with `--tray-helper`, URL+token
  over stdin, `ready|notray|quit` over stdout, `Pdeathsig=SIGTERM`.
- `tray_linux.go` `runApp`: decides tray/no-tray before serving.
- `main.go`: local token minted after owning the port; `openDashboard` opens the
  browser 1.5 s after start; "already running → open and exit" handoff;
  `RESTART_WAIT` retry loop on bind.
- `actions.go` `relaunchSelf` (Restart now), `isElevated`, `startupBanner`.
- Data layout: `.env`, `efemon.db`, `efemon-token`, `efemon.log`, TLS cert/key
  live next to the executable (`appDir`).

## Command line

Today the only argument is the internal `--tray-helper`. A minimal `flag`
parse (standard library) adds:

| Flag | Effect |
|---|---|
| `--version` | print `efemon <appVersion>` and exit, before log/DB are touched |
| `--no-browser` | start without opening the browser; tray still shown |
| `--service` | service mode: implies `--no-browser`; session watcher on; Quit/Restart/Stop go through `systemctl`. Also inferred from the `INVOCATION_ID` environment variable systemd sets, for a unit edited by hand |
| `--install-service` | install and start (root) |
| `--uninstall-service` | stop, disable, remove the unit (root) |
| `--service-status` | print installed/active/path; exit 0 when installed and active, 1 otherwise |

Unknown flags: usage to stderr, exit 2. `--tray-helper` keeps its current
handling and runs before everything else.

## Installation

`--install-service` (and the UI action, see below) performs these idempotent
steps; each failure prints why and exits 1:

1. Require root and a `systemctl` on PATH. Without systemd (OpenRC, runit):
   "this system does not use systemd; run efemon from your session startup
   instead" — out of scope.
2. `mkdir -p /opt/efemon` (0700, root). Copy the running executable to
   `/opt/efemon/efemon` (0755) unless the running executable *is* that file
   (reinstalling from the installed copy only rewrites the unit).
3. **Data migration** — when `/opt/efemon` holds none of them yet: move (not
   copy) `.env`, `efemon.db` (+ `-wal`, `-shm`), `efemon-cert.pem`,
   `efemon-key.pem` from the original executable's directory. Token and logs
   are not moved: regenerated. Print what moved. From the CLI the moving
   process holds no DB, so it happens on the spot; from the UI see below.
4. Write `/etc/systemd/system/efemon.service`, `systemctl daemon-reload`,
   `systemctl enable --now efemon.service`.
5. If another instance owns the port, say so: "stop the manual instance; the
   service retries". The service already retries the bind (~10 s, `RESTART_WAIT`
   logic reused: service mode sets it) and has `Restart=on-failure`.

Unit file, generated by `unitFile(exe string) string` (pure, tested):

```ini
[Unit]
Description=eFe Process Monitor
Documentation=https://github.com/eFeSpain/efe-process-monitor
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/opt/efemon/efemon --service
WorkingDirectory=/opt/efemon
Restart=on-failure
RestartSec=2
# No systemd sandboxing: the monitor needs raw sockets (passive DNS), every
# process's /proc, nft/iptables, kill, and to start processes as the session
# user (setuid) — each hardening option breaks one of those.

[Install]
WantedBy=multi-user.target
```

`--uninstall-service`: `systemctl disable --now`, remove the unit,
`daemon-reload`. `/opt/efemon` is **kept** (forensic DB, `.env` with keys); the
command says so and prints the `rm -rf /opt/efemon` for whoever wants it.

Why `/opt/efemon` and not the current path: a root service starting from a
user-writable directory (`~/Downloads`) is exactly what the audit flags.

## Service mode at runtime

### Session watcher (`desktop_linux.go`)

`desktopUser()` stops being resolved once. A `sessionWatcher` holds
`current *desktopSession` under a mutex:

- Manual (`sudo`) mode is unchanged: `SUDO_UID`/`PKEXEC_UID` resolve at
  start-up, exactly as today. The watcher only runs with `--service`.
- In service mode there is no `SUDO_UID`. Every **5 s** the watcher lists
  `/run/user/*/bus`; a single uid ≠ 0 is the candidate (two or more: logged
  once — "several users have a session; tray disabled" — and nothing is
  guessed, as today). `/proc` is scanned (`sessionFor`) only when a new uid
  appears; with no candidate the tick does nothing expensive.
- With a session: `spawnTrayHelper(tokenURL(url, localToken), s)` as today;
  `current = s`. `runAsDesktopUser` reads `current` under the mutex; `nil`
  means notifications go to the log only, as they already do without a session.
- When the helper exits (logout: its bus is gone and `systray` returns; or it
  is killed) the watcher sets `current = nil` and resumes polling. Next login,
  new helper. One helper per session, never two.
- Log one line on attach and one on detach; the banner gets
  `[+] Mode            systemd service (desktop session: waiting / user X)`.

### Token

Minted at service start, written to `/opt/efemon/efemon-token` (0600 root) as
today. The helper receives the current token in the URL over stdin whenever it
is spawned — at boot or hours later at login.

### Quit, Restart, Stop

In service mode (`serviceMode` bool, set from the flag or `INVOCATION_ID`):

- Tray *Quit*: `systemctl stop efemon.service`. The process ends; the unit
  stays installed and comes back at the next boot. Menu text: "Stop until next
  boot".
- Settings *Restart now* (`handleRestart`): `systemctl restart efemon.service`
  instead of `relaunchSelf` — systemd would kill the relaunched child with the
  cgroup. The page already waits ~6.5 s and redirects to the new URL.
- Panel *Stop service* button (`handleShutdown`): `systemctl stop`.
- Without `--service` nothing changes.

### Browser

Never opened automatically in service mode (at boot there is nobody to open it
for). It opens from the tray, or by running `efemon` by hand: the second
instance finds the port taken and hands off — but as a non-root user it cannot
read the root-owned token, so it lands on the gate page. That already happens
under `sudo` today; the gate page text gains the hint "open the panel from the
tray icon, or run `sudo efemon`".

## Settings and API

`service_linux.go` (+ stubs in `service_other.go` returning `supported:false`):

- `GET /api/service` → `{"supported":true,"installed":bool,"active":bool,
  "mode":"service"|"manual","path":"/opt/efemon/efemon","elevated":bool}`.
  `installed` = unit file exists; `active` = `systemctl is-active`.
- `POST /api/service {"action":"install"|"uninstall"}` → `{"ok":true}` or
  `{"ok":false,"error":"…"}` with `systemctl`'s message. Requires elevation
  (403 "requires root" otherwise). Goes through `requireMethod`, `decodeJSON`
  and the gate like every other endpoint; logged as `SERVICE install|uninstall
  by operator`.

**Install from the UI, in two steps**, because the manual process holds the DB
open and owns the port:

1. The request handler copies the binary, writes the unit with an extra line
   `Environment=EFEMON_MIGRATE_FROM=<original appDir>`, runs `daemon-reload`
   and `enable` (not `--now`), responds `{"ok":true}`.
2. ~400 ms later (same pattern as Restart now) the manual process closes the
   DB, runs `systemctl start efemon.service` detached via `command()`, and
   exits. The page shows "installed — the service starts in a few seconds" and
   reloads after 6.5 s.
3. The service, at start-up, sees `EFEMON_MIGRATE_FROM`, performs the data
   migration (nobody holds the files any more), then rewrites the unit without
   that line and `daemon-reload`s. If `/opt/efemon` already has data, the
   variable is ignored and removed.

From the CLI the installing process has no DB open: migration happens in step 3
of *Installation* directly and the unit never carries the variable.

**UI**: a "Run at boot" block in ⚙ Settings, shown only when `supported`:
status pill (green "installed and active" / grey "not installed"), the path,
and one button — *Install as a service* or *Remove service* — with a confirm.
Not elevated: "requires root" and the button disabled. All strings in es/en/zh.

## Testing

Hermetic (`go test`):

- flag parsing: each flag sets its mode; unknown flag → exit 2 (via a
  `parseArgs(args) (opts, error)` pure function).
- `unitFile(exe)`: exact text, with and without the migration line.
- `migrationPlan(src, dst)` over `t.TempDir()`: which files move, skipping
  what already exists at `dst`, never the token or logs.
- `desktopUserCandidates`: already tested; add "no SUDO_UID, one uid" and
  "several uids → nil".
- `sessionWatcher` with an injected `probe func() *desktopSession` and
  `spawn func(*desktopSession) (done <-chan struct{}, ok bool)`: attaches when
  a session appears, detaches when the helper ends, never spawns twice,
  re-attaches after a detach.
- `/api/service`: not elevated → 403; `service_other` → `supported:false`;
  POST with a bad action → 400.

Manual, by the user (root + systemd + a desktop session): install from CLI,
reboot, confirm the service is active before login and the tray appears at
login; log out/in and see the helper respawn; Quit from the tray; Restart now
from Settings; install from the UI on a fresh checkout; uninstall. A script
with these steps and what to look for in `efemon.log` accompanies the plan.

## Out of scope

Windows (second delivery); running as a non-root user; several graphical users
at once (logged, not chosen); systems without systemd; macOS; the user `.env`
staying in the original directory (it moves to `/opt/efemon`).
